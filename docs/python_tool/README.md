# Tutorial 13: Tutorial 13: EDF Trace Analysis Visualization using `python_tool`

## Introduction 
In the previous tutorials, Eclipse Trace Client was used for trace visualization. It is a strong and reliable tool because it allows precise cursor-based timing analysis. However, understanding the overall scheduling behavior from the trace view can still be difficult.

In this tutorial, we use a Python-based tool to visualize EDF scheduler traces in a clearer way. The tool helps show task execution order, deadline behavior, period counts, and idle time. In the second section, we also introduce a simpler version of the visualization tool, which can be used for other trace experiments such as PIP and PCP.

An important change in this tutorial is the simulation stop mechanism. Previously, a DUMP task was used to stop the simulation after a fixed duration by assigning it a very high priority. This approach worked for fixed-priority scheduling, but it is not reliable for EDF because scheduling decisions are based on absolute deadlines, not only on static task priority. For example, if the DUMP task is expected to stop the simulation at 700 ms, it may still be delayed until the CPU becomes available and the scheduler selects it.

To avoid this problem, this tutorial uses the `rtems_timer_fire_after()` API. This RTEMS timer mechanism allows the simulation run to be stopped after a fixed time without depending on a normal scheduled task.

## Understanding Python Tool

The Python tool is used to visualize RTEMS EDF trace data in a clearer way. In previous tutorials, Eclipse Trace Client was used for trace visualization. It is still useful for checking exact timing values, but understanding the complete scheduling behavior can become difficult from the raw trace view.

This tool reads the exported RTEMS trace file and generates a graphical view of the EDF scheduler behavior. It helps to visualize:

* `task execution timeline`
* `period count events`
* `deadline arrows`
* `IDLE time`
* `task preemption`
* `scheduler behavior over time`

In this example, the RTEMS application produces custom user events using `rtems_record_produce()`. These events are mainly period count events, but the Python tool also uses them as reference markers to reconstruct task releases and deadlines.

For example:

```c
#define EVT_COUNT_A RTEMS_RECORD_USER(0)   /// TASK A
#define EVT_COUNT_B RTEMS_RECORD_USER(1)   /// TASK B
#define EVT_COUNT_C RTEMS_RECORD_USER(2)   /// TASK C
```

Inside each task, the current period count is recorded:

```c
rtems_record_produce(EVT_COUNT_A, (uint32_t)stats.count);
```

So the trace contains `USER_0`, `USER_1`, and `USER_2` events. These events represent the period count of each task and are also used by the Python tool to identify the job order for plotting.

## Tool Working Overview

The Python tool starts working after the RTEMS trace log has been exported into a `.csv` or `.txt` file. This exported file contains scheduler events, task switch information, and custom RTEMS user events produced by the application.

The tool is executed from the command line as:

```bash
python3 rtems_edf_visualizer.py trace.csv
```

Here, `trace.csv` is the exported RTEMS trace file.

---

## 1. Reading the Trace File

The tool first opens the trace file passed from the command line.

```python
data = parse_trace(sys.argv[1])
```

The `parse_trace()` function reads the file line by line and sends each line to the log parser.

```python
with open(filepath, 'r') as f:
    for line in f:
        ev = parse_log_line(line)
```

Each valid line is converted into an event dictionary. Invalid lines, empty lines, or header lines are ignored.

---

## 2. Parsing Timestamp Information

Each trace event contains a timestamp. The tool converts this timestamp into absolute microseconds.

Example timestamp format:

```text
HH:MM:SS.mmm uuu nnn
```

The parser converts it into one value:

```text
absolute time in microseconds
```

This makes it easier to calculate time differences between events.

Later, the tool converts this absolute time into relative milliseconds for plotting.

```text
relative time = event time - first task start time
```

So the plot starts close to `0 ms` instead of using large absolute timestamp values.

---

## 3. Parsing Scheduler Switch Events

The most important events for the timeline are:

```text
sched_switch
```

These events show when the scheduler switches from one task to another.

From each `sched_switch` event, the tool extracts:

```text
previous task
next task
timestamp
```

For example, if the scheduler switches to Task A, the tool reads the `next_comm` field and stores that Task A started running at that time.

The tool then compares each scheduler switch with the next scheduler switch to create execution blocks.

```text
task start time = current sched_switch time
task end time   = next sched_switch time
duration        = end time - start time
```

Example:

```text
TA starts at 100 ms
next switch happens at 120 ms
TA execution block = 20 ms
```

These execution blocks are later drawn as colored boxes in the timeline.

---

## 4. Reading Count Events

The RTEMS application produces custom user events using `rtems_record_produce()`.

Example:

```c
rtems_record_produce(EVT_COUNT_A, (uint32_t)stats.count);
```

The events are defined as:

```c
#define EVT_COUNT_A RTEMS_RECORD_USER(0)
#define EVT_COUNT_B RTEMS_RECORD_USER(1)
#define EVT_COUNT_C RTEMS_RECORD_USER(2)
```

In the trace file, these appear as:

```text
USER_0
USER_1
USER_2
```

These are mainly `period count events`. They store the current `stats.count` value of each task.

The Python tool uses these count events for two purposes:

```text
1. to plot the period count graph
2. to reconstruct job release times and deadlines
```

So, these events are not separate deadline events. They are count events, but they also act as reference points for the visualizer.

---

## 6. Reconstructing Release Times

A count event may not always appear exactly at the real task release time.

For example, Task B may become ready at `300 ms`, but if Task A is already running, Task B may not execute immediately. Since the count event is produced inside the task, the `USER_1` event may appear later than `300 ms`.

Because of this, the tool does not directly use the count event timestamp as the release time for every job.

Instead, it uses the count value to calculate the job index.

```text
job index = current count value - first count value
```

Then it reconstructs the theoretical release time:

```text
release time = first count event time + job index × period
```

After that, it calculates the absolute deadline:

```text
deadline = release time + relative deadline
```

Example for Task A:

```text
period = 100 ms
relative deadline = 100 ms
first count event time = 0 ms
first count value = 1
```

If the tool later reads:

```text
USER_0 data = 0x3
```

then:

```text
current count value = 3
job index = 3 - 1 = 2
release time = 0 ms + 2 × 100 ms = 200 ms
deadline = 200 ms + 100 ms = 300 ms
```

So the third recorded period of Task A is plotted with:

```text
release time = 200 ms
deadline = 300 ms
```

This method gives cleaner deadline arrows, especially when a task records its count event later because it was not scheduled immediately.

---

## 7. Building the Timeline

After parsing the scheduler switches, the tool builds execution segments.

Each segment contains:

```text
task name
start time
end time
duration
```

Example:

```text
TA runs from 100 ms to 120 ms
TB runs from 120 ms to 135 ms
IDLE runs from 135 ms to 150 ms
```

The tool then assigns each task to a separate horizontal lane.

The configured tasks are placed first:

```text
Task A
Task B
Task C
```

Other detected threads are placed after them, and `IDLE` is placed separately.

Each task gets a color from the config file.

---

## 8. Drawing Deadline Arrows

For each task, the tool draws deadline arrows using the reconstructed release time and calculated deadline.

Each arrow starts at:

```text
release time
```

and ends at:

```text
absolute deadline
```

For example:

```text
Task A release = 200 ms
Task A deadline = 300 ms
```

The arrow is drawn from `200 ms` to `300 ms`.

The label above the arrow shows the period count and deadline length, for example:

Here, P3 means the task event contained count value 3, and 100.0ms shows the relative deadline duration.

```text
P3: 100.0ms
```

If a deadline goes beyond the trace end time, it can be hidden using:

```python
SHOW_INCOMPLETE_DEADLINES = False
```

This keeps the final plot cleaner.

---

## 9. Drawing the Period Count Graph

The lower graph shows how the period count changes over time.

For each task, the tool uses the same count events:

```text
USER_0
USER_1
USER_2
```

The x-axis shows time in milliseconds, and the y-axis shows the count value.

This graph helps confirm that each task is releasing periodically and that the recorded counts are increasing correctly.

## Summary

The complete flow of the tool is:

```text
RTEMS trace file
        ↓
read log file
        ↓
parse timestamps
        ↓
parse sched_switch events
        ↓
build task execution timeline
        ↓
read USER_0 / USER_1 / USER_2 count events
        ↓
use config file for period and deadline values
        ↓
calculate job index from count value
        ↓
reconstruct release times
        ↓
calculate deadlines
        ↓
draw EDF timeline and period count graph
        ↓
save output image
```

The key idea is that the custom RTEMS user events are count events. The Python tool uses these count values together with the task configuration to reconstruct the expected EDF timing behavior and generate a clear visualization.




## Example

Example code is provided in [tutorial13](docs/Tutorial13.zip), and the Python visualization tool with sample trace logs is provided in the [python_tool](python_tool) folder.

In this example, three periodic tasks are created under the EDF scheduler:

```text
Task A period = 100 ms
Task B period = 150 ms
Task C period = 200 ms
```

All tasks are created with the same base priority, but under EDF scheduling the execution order is decided based on the absolute deadlines generated by `rtems_rate_monotonic_period()`.

Each task records its period count using the RTEMS Record API:

```c
#define EVT_COUNT_A RTEMS_RECORD_USER(0)
#define EVT_COUNT_B RTEMS_RECORD_USER(1)
#define EVT_COUNT_C RTEMS_RECORD_USER(2)
```

These events appear in the trace as:

```text
USER_0
USER_1
USER_2
```

The recorded count values are used by the Python tool to plot the period count graph and reconstruct the release time and deadline of each task job.

Deadline miss events are also defined:

```c
#define EVT_MISS_A RTEMS_RECORD_USER(3)
#define EVT_MISS_B RTEMS_RECORD_USER(4)
#define EVT_MISS_C RTEMS_RECORD_USER(5)
```

If `rtems_rate_monotonic_period()` returns `RTEMS_TIMEOUT`, the corresponding deadline miss event is recorded.

This example also uses `rtems_timer_fire_after()` to stop the trace run after `700 ms`. This replaces the older DUMP task approach. The timer callback stops the run using:

```c
rtems_fatal_error_occurred(0xDEADBEEF);
```

This is more suitable for EDF because the stop mechanism does not need to wait for a normal EDF-scheduled task to get CPU time.

## Deadline Miss Example

Example code is provided in [tutorial13_b](docs/Tutorial13_b.zip), and the trace file `trace_13_b.csv` is provided in the [python_tool](python_tool) folder.

This example uses the same three EDF periodic tasks:

```text
Task A period = 100 ms
Task B period = 150 ms
Task C period = 200 ms
```

In this case, Task B is intentionally made heavier by increasing its workload:

```c
for (volatile int i = 0; i < 14000 * 6; i++); 120ms
```

This increases the execution time of Task B and creates a deadline-miss scenario. Under EDF scheduling, the task with the earliest absolute deadline should run first. However, if a task takes too much CPU time, other tasks may be delayed and may not complete within their deadline window.

A deadline miss is detected when `rtems_rate_monotonic_period()` returns `RTEMS_TIMEOUT`. In the code, each task checks this return value and records a deadline miss event:

```c
if (sc == RTEMS_TIMEOUT) {
    rtems_record_produce(EVT_MISS_B, (uint32_t)stats.count);
    printf("Task B missed deadline, count=%lu\n",
           (unsigned long)stats.count);
}
```

Example output from the run:

```text
Task B missed deadline, count=2
Task A missed deadline, count=5
Task B missed deadline, count=3
Task B missed deadline, count=4
```

This shows that Task B missed multiple deadlines because its workload was too long. Task A also missed a deadline later because the heavy execution of Task B affected the overall schedule.

The generated visualization is shown below:

![output3](/docs/python_tool/docs/3.png)

In the timeline, Task B has much longer execution blocks compared to the normal case. These long blocks reduce the available CPU time for Task A and Task C. The deadline arrows show the expected release-to-deadline windows, while the execution blocks show when each task actually received CPU time.

If a task execution extends too close to, or beyond, its deadline window, the next call to `rtems_rate_monotonic_period()` can report `RTEMS_TIMEOUT`. This means the task was not able to maintain its required periodic timing.

The lower graph shows the period count values over time. It helps confirm which task periods were reached during the trace run and connects the printed deadline-miss count values with the plotted period counts.

Since the trace run ends at around `700 ms`, incomplete deadline arrows are not shown. Any task period whose deadline goes beyond the trace end time is hidden to keep the plot clean.

## Custom Events Used in Code

In the RTEMS application, custom events are produced using the RTEMS Record API:

```c
#define EVT_HIGH   RTEMS_RECORD_USER(1)
#define EVT_MED    RTEMS_RECORD_USER(2)
#define EVT_LOW    RTEMS_RECORD_USER(3)
```

The event data is used to describe the task behavior:

```c
#define REQ     1
#define GOT     2
#define REL     3
#define woke_up 5
```

For example:

```c
rtems_record_produce(EVT_HIGH, REQ);
rtems_record_produce(EVT_HIGH, GOT);
rtems_record_produce(EVT_HIGH, REL);
```

These events are later shown in the plot as labels such as:

```text
HIGH: REQ SEM
HIGH: GOT SEM
HIGH: REL SEM
MED: woke_up
LOW: GOT SEM
LOW: REL SEM
```

This makes the trace easier to understand compared to looking only at raw scheduler switches.

## Understanding the Config File

The important part of this tool is the [config](python_tool_simple_visualizer/rtems_behavior_config.py)
 file. The config controls task names, event mapping, labels, colors, text size, and legend position.

Task names are defined in the `THREADS` section:

```python
THREADS = {
    'HIGH': {'label': 'High priority task'},
    'MED':  {'label': 'Medium priority task'},
    'LOW':  {'label': 'Low priority task'},
}
```

Custom events are mapped to task lanes using the `EVENTS` section:

```python
EVENTS = {
    'USER_1': {'label': 'HIGH', 'map_to': 'HIGH'},
    'USER_2': {'label': 'MED',  'map_to': 'MED'},
    'USER_3': {'label': 'LOW',  'map_to': 'LOW'},
}
```

Event data values are converted into readable labels using:

```python
EVENT_DATA_LABELS = {
    1: 'REQ SEM',
    2: 'GOT SEM',
    3: 'REL SEM',
    5: 'woke_up',
}
```

If event data is missing, the tool shows only the event label. If data exists but is not listed in `EVENT_DATA_LABELS`, the tool prints the raw value as `data=<value>`.

Event labels can be enabled or disabled using:

```python
SHOW_USER_EVENTS = True
SHOW_EVENT_DATA_LABELS = True
SHOW_RAW_DATA_IF_UNKNOWN = True
```

---

`MIN_BOX_TEXT_DURATION_MS = 2.0` in `rtems_behavior_config.py` means duration text is shown only for execution blocks longer than `2 ms`, which avoids unreadable text inside very small blocks.
