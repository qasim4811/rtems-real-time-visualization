# Tutorial 6: High-Frequency Logging and Buffer Saturation
> **Goal:** This analysis explores how to select the correct capture window for trace events.

## Introduction
In RTEMS, the "window" for capturing events is physically limited by the Ring Buffer size. This is configured in our code using the macro init.c:
```#define CONFIGURE_RECORD_PER_PROCESSOR_ITEMS 65536.```

- Capacity: This specific value allows the system to store exactly 65,536 individual items before it reaches its limit.

- The "Window" Concept: The "window size" is not just about time (milliseconds); it is about the number of events. If the tasks generate 1,000 events per second, so  window should be roughly 65 seconds long.you can change the Event record capacity as per your requirements,for this tutorial i am using size of 65536.

### Example:
An example is already available in the GitHub repository [repo](/Pre-built_Rtems_Toolsuite_BSP) under the name Tutorial6. In this case, I generate approximately 153,000 custom events, with each event taking about 0.015 ms to generate, as shown in the figure below. If the window size is set to 500 ms, only around 33,333 events are generated, which is not sufficient to fill the ring buffer. Therefore, I extend the capture window to  1500 ms.

 ```bash
rtems_task Task_B(rtems_task_argument arg) {
 for (volatile int i = 0; i < 153000; i++){
    rtems_record_produce(EVT_TB, 1);///producing custom event and sending data 0x01
    // Wait 5sms 
    }
    rtems_task_wake_after(RTEMS_MILLISECONDS_TO_TICKS(5)); 
    rtems_task_delete(RTEMS_SELF);
}
```
 ```bash
rtems_task Dump_Task(rtems_task_argument arg) {
    rtems_task_wake_after(RTEMS_MILLISECONDS_TO_TICKS(1500));
    rtems_record_produce(EVT_DUMP, 0);///producing custom event after wakeup,sending data 0x00
    rtems_fatal_error_occurred(0xDEADBEEF);
}

```

As shown in the figure below, we have lost the records for the Init task, Task A, and the start of the DUMP task.

- Buffer Saturation: Because the Ring Buffer is limited to 65,536 items, the 153,000 events generated by Task B caused the buffer to "wrap around" and overwrite the initial records.

- The Window Effect: Our capture window was set to 1500ms, allowing Task B to complete its massive loop. If we had chosen a smaller window (e.g., 500ms), the simulation would have ended before the overflow occurred, preserving the early records.

- If you are interested in high-frequency logging and set the capture window to 500 ms while increasing the event record size to 160,000 in init.c, you will be able to preserve events from other tasks. However, you will not be able to fully capture Task B events, as the DUMP task will wake up and trigger a fatal error. In this case, it is recommended to increase the capture window (for example, from 500 ms to 1500 ms)

![Help](/docs/Ring_Buffer/docs/2.png)

To maintain data integrity in high-speed systems, you must carefully balance two parameters in init.c and main.c:

- Event Record Size: Increase CONFIGURE_RECORD_PER_PROCESSOR_ITEMS to match your expected event density.

- Capture Window: Time your rtems_fatal_error_occurred  accordingly to preserve Events records.
